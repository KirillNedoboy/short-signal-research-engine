# Обновление только Lane C: runtime A и стратегический слой C

**Статус:** новая редакция; заменяет предыдущий план переноса. Реализация и переключение служб не выполнялись.
**Статус исполнения (2026-10-19 18:52:30 UTC):** implementation for the approved design, scoped Linux validation, and release provenance are complete (`51` scoped tests passed; final watermark guard passed); the isolated 24-hour shadow is **RUNNING** from verified start `2026-10-19 18:49:48 UTC`. The last status recorded `runtime_started=true`, readiness `false/process_started`, an active unit, `3` cycles / `300` coverage, no `429`, a closed isolation gate, approximately `2.6 MB` footprint, approximately `13.5 GiB` free disk, and unchanged production PIDs. Overall validation remains in progress; no 24-hour result or production cutover is claimed.
**Цель:** обновить только C: использовать архитектуру runtime работающей A как техническую основу и интегрировать собственный стратегический слой, состояние и гарантии сохранения C.
**Границы:** изменения исходников и развёртывания относятся к C. Исходники, конфигурации, БД и службы A/B служат эталонами для чтения. Общую библиотеку всех Lane в этой задаче не выделять.
**Поведение по умолчанию:** сохраняются формулы, пороги, включённые стратегии, feature semantics, правила допуска и форматы сообщений C. Дополнения торговой логики A автоматически не включаются.
**Исполнение:** Sol — план, Luna/Max — реализация; проверки только затронутых компонентов, без автоматического повторного аудита Sol.

## Брейншторм и выбранная архитектура

| Вариант | Что переносим | Цена и риск |
|---|---|---|
| **Выбран: runtime A как основа самостоятельной C** | WS/store, координатор, workers и lifecycle A; стратегический pipeline, состояние, persistence и доставка C подключаются через адаптеры | Новый composition root C позволяет явно разделить инфраструктуру и торговую логику |
| Последовательно ускорять старый монолит C | Кэш, оптимизация запросов и отдельные фоновые задачи в прежнем цикле | Меньше первоначальных изменений, но сохраняются связи между сканированием, доставкой и research |
| Собрать C заново на всём приложении A | Полный runtime, domain, features и storage A; затем дополнения C | Шире риск незаметной замены формул, состояния событий и идентификаторов |

Кандидат C строится вокруг инфраструктурных модулей A, а не вокруг последовательного `run_cycle` старой C. Новый composition root связывает market-data runtime, координатор, pipeline C и background workers. Pipeline C включает feature builder, реестр/адаптеры стратегий, предварительные проверки, lifecycle событий и финальный допуск; переносить только вызов реестра недостаточно. Signal identity, атомарное сохранение и исправления delivery funnel C остаются эталоном. Целиком копировать `main`, domain, repository или migrations A запрещено: там есть другие семантические изменения.

Новый поддерживаемый код размещается в `lanes/c/src/app`; проверки — в `lanes/c/tests`. Исторические экспортные снапшоты остаются неизменяемыми. Runtime-модули A входят в самодостаточную сборку C с закреплённым происхождением; импорт из работающей директории A или её `current` не используется. Launcher C получает явный источник нового immutable release и сохраняет собственный instance fence. Сборка фиксирует версии источников и список перенесённых инфраструктурных модулей; обновление источника A впоследствии выполняется явно с повторением совместимых проверок.

## 1. Зафиксировать эталон и границы переноса

- Перед реализацией повторно определить исходники по работающим PID и импортам. Исходная точка исследования: A `802014…`, C `aa4f402…`, репозиторий `5bbc015…`. При расхождении пересчитать diff до переноса.
- Составить машинно проверяемый перечень: параметры стратегий C, формулы/features, state transitions, идентичность и дедупликация, outbox, исправления funnel, schema и формат данных для research-collector. Рядом зафиксировать разрешённые изменения runtime и source hashes.
- Зафиксировать три интерфейса: market-data runtime выдаёт неизменяемый снимок с asof/quality; pipeline C принимает снимок и состояние и возвращает решение/изменение состояния; C persistence сохраняет итоговый bundle и outbox. Доставка и research выполняются после критического сохранения, вне ожидания минутного окна.
- Записать базовые метрики C: фазы загрузки свечей/стакана, features, стратегии, DB/outbox, outcomes; число запросов по endpoint, ожидание лимитера, возраст данных и покрытие. Базовую старую C воспроизвести на копии состояния/записанных входах; добавление таймингов в рабочую службу допускается только как согласованный production-шаг. В ускоренной версии эти измерения оставить постоянно.
- Изменения конфигурации разделить на runtime и стратегию: новые runtime-флаги не должны создавать новую логическую identity сигнала. Если существующий полный config fingerprint меняется, сохранить отдельный fingerprint исходных параметров стратегии и документировать связь версий.
- Критерий этапа: выбран один эталон C; каждому отличию от него назначена категория «перенос инфраструктуры», «адаптер» или «недопустимое изменение поведения».

## 2. Подключить быстрые данные и минутные окна

- Собрать новый composition root C на совместимом наборе WS hub, canonical frame store, continuity/repair, checkpoints и scan coordinator зафиксированной A. Прежний последовательный цикл C использовать только как reference в проверках. Зависимости закрепить для Python и пакетов C; проверять чистую установку, без vendor.
- Через адаптер передавать существующим features/StrategyContext C закрытые свечи, market_asof, decision_timestamp, состояние события, стакан и опциональные derivatives. Сохранить правила C для закрытой свечи, freshness, неизвестных значений и недоступных derivatives.
- WS/store становится основным источником свечей; REST — startup/backfill и восстановление конкретного пропуска. Полный повторный REST-prefetch всех монет в нормальном минутном окне исключить.
- Сохранить universe, shortlist_size=100, фильтры и правила ротации C. Активные события получают P0, остальные запланированные монеты — P1. Стартовые параметры runtime: окна раз в 60 секунд, два consumers, P0 deadline 15 секунд, P1 deadline 30 секунд, grace 30 секунд.
- Один symbol обрабатывается последовательно, включая fast monitor: блокировка на symbol и проверка порядка окон исключают запись старого состояния поверх нового. Каждая запланированная задача получает ровно один терминальный статус; deadline/неполные данные не считаются успешной оценкой.
- Пропуски, разрывы и устаревшие данные блокируют actionable-решение до восстановления. Перезапуск восстанавливает C state, прогревает данные и только после readiness допускает новые решения.
- Совпадающие запросы стакана объединять только внутри одной и той же оценки с одним asof. Сохранить отдельное свежее получение там, где C требует повторной проверки перед допуском/доставкой.

## 3. Убрать ожидание служебной работы из сканирования

- Сохранение финального сигнала и outbox остаётся атомарным по контракту C. Сканер сохраняет bundle и будит delivery worker; сетевую доставку выполняет один worker C с действующими lease/retry/dedup/funnel правилами.
- Outcome worker получает ограниченные batches и будится независимо от сканирования. Дополнить C tracker совместимыми необязательными batch-limit аргументами; определения результатов, горизонты и временные якоря C не менять.
- Research/coverage записи обслуживать через ограниченную очередь. Критические state/signal/outbox записи через неё не проводить. Переполнение некритической очереди публикует счётчик потерь; потерянную coverage-запись нельзя считать подтверждённым покрытием.
- Использовать приоритеты запросов A, сохранив лимиты C: concurrency 4, min delay 350 мс, jitter 100–300 мс. Outcome/recovery не занимают всю доступную capacity перед live scan. Повышение API-лимитов и CPUWeight в эту реализацию не включать.
- SQLAlchemy sessions не разделять между consumers/threads; C persistence и блокировки должны поддерживать конкуренцию. Shutdown останавливает admission, завершает/отменяет задачи по правилам A и освобождает fence без зависания.

## 4. Проверить равенство логики, скорость и отказы

- Старую C и кандидата запускать в разных интерпретаторах, чтобы пакеты с именем `app` не смешивались. Детерминированный replay подаёт одинаковые свечи/стакан/OI, timestamps, конфигурацию и начальное состояние.
- Для одинакового входа требовать 100% совпадения: features, strategy/subtype/model_version, actionable, score/grade, blockers/vetoes, уровни, state transitions и signal_identity. Допуски нужны только для технических метрик длительности, не для результата стратегии.
- Проверить точечно: forming candle, пропущенная/повторная/поздняя WS свеча, reconnect, REST timeout/429, deadline, конкурентный fast monitor, restart/checkpoint, повторное сохранение, pending outbox и конфликтующая аренда. Ошибка Telegram не должна останавливать минутные окна; сохранение/отправка должны сохранять существующие ограничения дедупликации.
- Проверить C storage и миграции на согласованной копии C БД. Исторические IDs и outbox остаются читаемыми старым runtime; допустимы только обратно совместимые добавления. Старые определения миграций не переписывать. Проверить чтение событий существующим research-collector.
- После прогрева выполнить не менее 120 минутных окон на 100 монетах: целевой p95 окна ≤20 секунд при доступных валидных данных; P0 p95 ≤15 секунд; успешно оценено ≥99% запланированных задач и не хуже эталонного покрытия. Отдельно показать stale/missing/deadline/error доли: ускорение за счёт пропуска задач не принимается.
- Учитывать возраст свечи по существующему порогу C, очередь доставки, event-loop lag, запросы, RAM, диск и backlog. Ориентир исследования: C/100 median 189,9 секунды, A/102–150 median 10,5 секунды. Цель скорости — условие приёмки, не обещание до измерения.
- Запускать целевые tests для этих контрактов и перенесённых модулей, проверку синтаксиса, зависимостей и загрузки конфигов. Полный test suite не запускать по умолчанию.

## 5. Выпустить C с контролируемым переключением и откатом

- Реализацию готовить в отдельной ветке. До допуска к серверу получить воспроизводимый release, чистые проверки, отчёт replay/parity, точные миграции и rollback-команду с сохранённой предыдущей версией.
- Затем провести 24 часа shadow как временный проверочный процесс C: отдельные state/DB/locks/runtime paths, отправка Telegram технически отключена, production DB A/B/C для него только read-only. Ограничить startup/backfill, память процесса — 2 ГиБ, хранилище shadow — 1 ГиБ; при заполнении прекратить запись сырых данных, сохранив сравнения решений. Остановить shadow при новых ответах 429, свободном диске менее 10 ГиБ либо росте p95 сканирования A/B более чем на 20% в двух последовательных 30-минутных интервалах относительно исходного периода с сопоставимой нагрузкой.
- В shadow разделять сравнения: одинаковый input/state обязан давать одинаковое решение; дополнительные решения из-за более ранней оценки классифицируются как эффект расписания и показываются отдельно. Нельзя обещать идентичный исторический список Telegram-сигналов после ускорения.
- Переключение рабочей C — отдельный production-шаг после рассмотрения готового отчёта пользователем. Перед ним выполнить согласованный SQLite backup, сохранить launcher/unit/config и pending outbox; остановить старого отправителя C, прогреть кандидата с закрытым delivery gate и затем открыть доставку ровно у одного владельца C.
- A/B и collector при переключении не перезапускать. Проверить минимум 60 окон после включения и продолжить наблюдение 24 часа. Немедленно закрыть допуск/доставку кандидата и откатить бинарник при нарушении identity/parity, повреждении состояния, потере outbox, двух владельцах доставки или неограниченном backlog. Три последовательных незавершённых окна также запускают откат; деградацию по скорости/покрытию оценивать на последних 60 окнах.
- Откат возвращает прежний release и runtime config, сохраняя актуальную совместимую БД и очередь. Backup не восстанавливать поверх новых событий автоматически; при необходимости восстановления сначала согласовать новые записи и outbox, чтобы не потерять историю и не повторить доставку.
- По завершении обновить инструкции C, манифест происхождения, SHA-256 и результаты измерений. В отчёте отдельно показать diff относительно обоих закреплённых источников и подтвердить отсутствие изменений A/B. Сверить launch source, release manifest и реально импортированный код, чтобы следующий запуск использовал проверенную сборку.

**Результат приёмки:** C сохраняет собственную логику на одинаковых входах, обрабатывает минутные окна в пределах целевой задержки, устойчиво переживает разрывы/перезапуск и допускает возврат к прежнему runtime без потери состояния.
